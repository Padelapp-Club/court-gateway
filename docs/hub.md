# Хаб: руководство оператора

Хаб — та же программа `court-gateway` в режиме `hub`. Он единственный открыт в интернет:
принимает партнёров по их ключам, держит исходящие подключения шлюзов клубов, передаёт запросы
партнёров нужному шлюзу и раз в минуту проверяет каждый шлюз.

```
партнёр ──HTTPS──▶ хаб ◀──HTTPS (исходящее от клуба, long-poll)── шлюз клуба ──▶ CRM клуба
```

## Как устроена связь

Шлюз держит несколько (по умолчанию 4) запросов `POST /tunnel/poll` к хабу. Хаб сразу отвечает
заголовками (шлюз знает, что он на связи) и держит тело ответа до 25 секунд: если за это время
пришёл запрос партнёра к этому клубу, хаб отдаёт его в теле ответа, шлюз выполняет его у себя и
присылает ответ `POST /tunnel/reply` с тем же идентификатором. Пустое тело — ждать снова. Все
запросы одного шлюза идут по одному соединению HTTP/2.

- Шлюз проверяет хаб по TLS-сертификату (системные корневые сертификаты; для своего центра
  сертификации — `hub.ca_file` у шлюза). Хаб узнаёт шлюз по его секрету (`Authorization: Bearer`).
  Поэтому запрос, пришедший шлюзу в ответе на poll, заведомо от хаба.
- Через туннель шлюзу доступны только `/v1/…` и `/health/…`. Ключ партнёра шлюзу не передаётся;
  передаётся имя партнёра, которое хаб проверил сам.
- Пределы: тело запроса партнёра — 1 МБ, ответ шлюза — 4 МБ, ответ ждётся `request_timeout`
  (30 с) плюс 5 с.
- Шлюз не на связи → партнёр сразу получает `503 CLUB_OFFLINE`; шлюз не ответил вовремя → `504
  CLUB_TIMEOUT`. У каждого ответа `X-Request-ID`, тот же идентификатор пишется в журнал хаба и шлюза.
- Обрыв, смена IP, перезапуск хаба: запросы шлюза падают, и он переподключается с экспоненциальной
  паузой от 1 до 60 секунд со случайным разбросом (чтобы все клубы не пришли разом).

## Запуск

Конфигурация — [hub.example.yaml](../hub.example.yaml), секреты — в переменных окружения или в
`.env` рядом с `hub.yaml`:

```sh
# hub.yaml + .env с HUB_OPERATOR_KEY, PARTNER_KEY_1, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID
court-gateway hub -config /etc/court-gateway-hub/hub.yaml
```

**TLS.** Либо хаб сам отдаёт HTTPS (`tls.cert_file`, `tls.key_file`), либо стоит за прокси,
который снимает TLS (тогда раздела `tls` нет и хаб слушает HTTP на внутреннем адресе). У прокси
таймаут ответа должен быть не меньше 60 секунд (long-poll держится 25 с) и не должно быть
буферизации ответов: хаб сразу отправляет заголовки, а тело позже.

**Docker:**

```yaml
services:
  hub:
    image: court-gateway:local
    command: ["hub", "-config", "/config/hub.yaml"]
    restart: unless-stopped
    env_file: hub.env
    ports: ["443:8443"]
    volumes:
      - ./hub:/config:ro                       # hub.yaml, tls.crt, tls.key
      - hub-state:/home/nonroot                # в hub.yaml: state_dir: /home/nonroot/hub-state
    healthcheck:
      test: ["CMD", "/court-gateway", "healthcheck", "-hub", "/config/hub.yaml"]
volumes:
  hub-state:
```

`state_dir` хаба нужно сохранять и резервировать: там зарегистрированные шлюзы (только SHA-256
секретов, самих секретов нет) и неиспользованные коды. Если каталог потерян, все клубы должны
подключиться заново с новыми кодами.

## Подключение клуба

```sh
court-gateway hub join-code create -config hub.yaml --club my-club --name "Мой клуб" [--ttl 24h]
```

Команда печатает одноразовый код (`XXXX-XXXX-XXXX-XXXX`, действует сутки) и адрес хаба
(`public_url`). Передайте клубу код и адрес. Шлюз обменяет код на постоянный секрет при `setup`;
повторно код не принимается, просроченный — тоже, а хаб не говорит, какая из причин. Новый код
для того же клуба при использовании заменяет прежний секрет (старый шлюз теряет доступ).

Команду можно выполнять на работающем хабе (в Docker: `docker exec <контейнер> /court-gateway hub
join-code create …`): коды хранятся отдельными файлами и читаются в момент обмена.

Отозвать подключение клуба: `court-gateway hub gateway revoke -config hub.yaml --club my-club`.
Работающий хаб перестаёт принимать секрет этого шлюза при следующем запросе.

## Ключи партнёров

```yaml
partners:
  - name: aggregator
    key_env: PARTNER_KEY_1          # не короче 24 символов: openssl rand -hex 32
    scopes: [read, book]            # read — сверка; book — ещё и бронирование
    clubs: ["*"]                    # или список клубов
    writes_per_minute: 60           # лимит бронирований по ключу
```

Ключи сравниваются за постоянное время и не попадают в журналы. Клуб, к которому у партнёра нет
доступа, для него выглядит как несуществующий (`404`).

## Мониторинг и уведомления

Каждые `heartbeat.interval` (60 с) хаб смотрит на каждый зарегистрированный шлюз:

- нет подключения дольше `offline_after` (3 мин) → «НЕТ СВЯЗИ»; при возвращении — «снова на связи».
  С интервалом 60 с уведомление приходит через 3–4 минуты после пропажи;
- на связи — хаб запрашивает у шлюза `/health/ready` через туннель (вход в CRM и узкий запрос
  занятости); `ready_failures` (3) неудачи подряд → «НЕ ГОТОВ: <код>» (`CRM_AUTH_FAILED`,
  `CRM_UNREACHABLE`, `TUNNEL_TIMEOUT` …); после успешной проверки — «снова готов».

Шлюз, не появившийся после перезапуска хаба, считается пропавшим с момента запуска хаба —
перезапуск не скрывает мёртвый клуб. Уведомление повторно не шлётся, пока состояние не изменится.

Куда: Telegram (`alerts.telegram`: токен бота и id чата из переменных окружения) и/или webhook
(`alerts.webhook_url_env`; POST JSON `{event, club, club_name, text, time}`, `event` —
`offline`, `online`, `not_ready`, `ready`). Текст содержит только id и название клуба, время и код
причины; секретов в нём нет. Ошибки доставки пишутся в журнал без адреса (в адресе Telegram — токен).

## Состояние клубов

```sh
curl -s -H "Authorization: Bearer $HUB_OPERATOR_KEY" https://hub.example.com/hub/status
```

```json
{"time": "…", "latest_version": "0.2.0", "clubs": [
  {"club": "my-club", "name": "Мой клуб", "connected": true, "last_seen": "…",
   "version": "0.1.0", "build": "release", "platform": "windows-amd64", "outdated": true,
   "ready": true, "last_check": "…", "registered_at": "…"}
]}
```

`build: selfbuilt` — клуб собрал программу сам, она не обновляется автоматически; `outdated` —
версия ниже `latest_version`. Если задать `latest_version`, хаб подсказывает официальным сборкам
обновиться сразу, не дожидаясь суточной проверки.

## Выпуски и подписи

Автообновление доверяет только манифесту, подписанному ключом выпусков (ed25519). Открытый ключ
вшивается в официальные сборки (`-X main.releaseKey=…`) и публикуется в репозитории как
`release.pub`; закрытый ключ хранится вне репозитория и никогда не коммитится.

```sh
go run ./tools/release keygen -out release.key        # один раз; печатает открытый ключ → release.pub
RELEASE_KEY="$(cat release.pub)" VERSION=0.2.0 scripts/build.sh
go run ./tools/release manifest -version 0.2.0 -dist dist -key release.key \
  -base-url https://github.com/Padelapp-Club/court-gateway/releases/download/v0.2.0
# загрузить в выпуск: бинарники, SHA256SUMS, manifest.json, manifest.json.sig
```

Шлюз ищет `https://github.com/Padelapp-Club/court-gateway/releases/latest/download/manifest.json`
(у шлюза можно переопределить `update.manifest_url`). Ставится только версия новее текущей, с
совпавшей суммой файла, прошедшая самопроверку (`court-gateway selfcheck`) с живой конфигурацией
клуба; после переключения у неё 3 минуты, чтобы войти в CRM и подключиться к хабу, иначе шлюз
возвращает прежний бинарник и не пробует эту версию 72 часа.
