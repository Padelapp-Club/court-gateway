# Хаб: руководство оператора

Хаб — та же программа `court-gateway` в режиме `hub`. Он единственный открыт в интернет:
принимает партнёров по их ключам, держит исходящие подключения шлюзов, передаёт запросы
партнёров нужному шлюзу, хранит конфигурацию клубов и следит за сигналами, которые шлюзы
присылают раз в минуту.

**Установка и клубы.** Одна установка шлюза — одна учётная запись CRM, в которой может быть
несколько клубов (сеть). Клуб ставит шлюз один раз: вводит код подключения и логин CRM — и больше
ничего не делает, даже когда в сети появляется новый клуб. Идентификатор установки назначает хаб,
клубы установки (название, часовой пояс, сетка, часы, корты, услуги) оператор задаёт на хабе через
операторское API — обычно из своей админ-панели. Партнёры обращаются к клубу по его `club_id`; хаб
знает, какая установка его обслуживает.

```
партнёр ──HTTPS──▶ хаб ◀──HTTPS (исходящее от клуба, long-poll)── шлюз клуба ──▶ CRM клуба
```

## Как устроена связь

Шлюз держит несколько (по умолчанию 4) запросов `POST /tunnel/poll` к хабу. Хаб сразу отвечает
заголовками (шлюз знает, что он на связи) и держит тело ответа до 25 секунд: если за это время
пришёл запрос партнёра к этому клубу, хаб отдаёт его в теле ответа, шлюз выполняет его у себя и
присылает ответ `POST /tunnel/reply` с тем же идентификатором. Пустое тело — ждать снова. Все
запросы одного шлюза идут по одному соединению HTTP/2.

- Шлюз проверяет хаб по TLS-сертификату (системные корневые сертификаты; для своего центра
  сертификации — `hub.ca_file` у шлюза). Хаб узнаёт шлюз по его секрету (`Authorization: Bearer`).
  Поэтому запрос, пришедший шлюзу в ответе на poll, заведомо от хаба.
- Конфигурация клубов: в каждом ответе на poll и на сигнал хаб ставит заголовок
  `X-Config-Version` — текущую версию конфигурации клубов установки. Если она отличается от той,
  на которой работает шлюз, шлюз забирает `GET /tunnel/config`, проверяет каждый клуб своим
  драйвером CRM и подменяет весь набор клубов разом, без перезапуска. Конфигурация живёт только в
  памяти шлюза. Не прошедшую проверку конфигурацию шлюз не применяет: работает на прежней и
  сообщает причину в сигналах (`config_error`).
- Через туннель шлюзу доступны только `/v1/…`, `/health/…` и `POST /gateway/discover` (чтение CRM
  для черновика клуба, только по запросу оператора). Ключ партнёра шлюзу не передаётся;
  передаётся имя партнёра, которое хаб проверил сам. Сам хаб через туннель в CRM клуба не ходит:
  о своём состоянии шлюз сообщает сам (см. «Мониторинг»).
- Пределы: тело запроса партнёра — 1 МБ, ответ шлюза — 4 МБ, ответ ждётся `request_timeout`
  (30 с) плюс 5 с.
- Шлюз не на связи → партнёр сразу получает `503 CLUB_OFFLINE`; шлюз не ответил вовремя → `504
  CLUB_TIMEOUT`. У каждого ответа `X-Request-ID`, тот же идентификатор пишется в журнал хаба и шлюза.
- Обрыв, смена IP, перезапуск хаба: запросы шлюза падают, и он переподключается с экспоненциальной
  паузой от 1 до 60 секунд со случайным разбросом (чтобы все клубы не пришли разом).

## Запуск

Конфигурация — [hub.example.yaml](../hub.example.yaml), секреты — в переменных окружения или в
`.env` рядом с `hub.yaml`:

```sh
# hub.yaml + .env с HUB_OPERATOR_KEY, PARTNER_KEY_1
court-gateway hub -config /etc/court-gateway-hub/hub.yaml
```

**TLS.** Либо хаб сам отдаёт HTTPS (`tls.cert_file`, `tls.key_file`), либо стоит за прокси,
который снимает TLS (тогда раздела `tls` нет и хаб слушает HTTP на внутреннем адресе). У прокси
таймаут ответа должен быть не меньше 60 секунд (long-poll держится 25 с) и не должно быть
буферизации ответов: хаб сразу отправляет заголовки, а тело позже.

**Префикс пути.** Хаб можно опубликовать не в корне домена, а под префиксом, например
`https://hub.example.test/gateway-hub`, если прокси снимает префикс перед хабом (nginx:
`location /gateway-hub/ { proxy_pass http://hub:8443/; }`). Тогда `public_url` хаба и `hub.url`
шлюза пишутся с префиксом, а шлюзы и партнёры обращаются к `<адрес>/tunnel/…` и `<адрес>/v1/…`.

**Docker:**

```yaml
services:
  hub:
    image: court-gateway:local
    command: ["hub", "-config", "/config/hub.yaml"]
    restart: unless-stopped
    env_file: hub.env
    ports: ["443:8443"]
    volumes:
      - ./hub:/config:ro                       # hub.yaml, tls.crt, tls.key
      - hub-state:/home/nonroot                # в hub.yaml: state_dir: /home/nonroot/hub-state
      - ./hub-status:/status                   # в hub.yaml: status_dir: /status — читает внешняя проверка
    healthcheck:
      test: ["CMD", "/court-gateway", "healthcheck", "-hub", "/config/hub.yaml"]
volumes:
  hub-state:
```

`state_dir` хаба нужно сохранять и резервировать: там установки с конфигурацией их клубов,
зарегистрированные шлюзы (только SHA-256 секретов, самих секретов нет) и неиспользованные коды.
Если каталог потерян, все установки должны подключиться заново с новыми кодами, а клубы — быть
заведены заново.

## Операторское API: установки, коды, клубы

Все запросы — с ключом оператора (`operator_key_env`), `Authorization: Bearer`; ключ сравнивается
за постоянное время. Без ключа или с неверным — `401`. Ошибки — `{"code", "message", "request_id"}`.
Идентификаторы установок и клубов — `[a-z0-9][a-z0-9-]{1,62}`.

```sh
H=https://hub.example.test
AUTH="Authorization: Bearer $HUB_OPERATOR_KEY"

# 1. установка = учётная запись CRM клуба или сети
curl -s -H "$AUTH" -X POST $H/hub/installations \
  -d '{"installation_id": "my-net", "name": "Моя сеть"}'
# 201 {"installation_id":"my-net","name":"Моя сеть","created_at":"…","config_version":0,"clubs":[],"gateway":null}

# 2. код подключения — его клуб вводит при установке (покажите его в админ-панели)
curl -s -H "$AUTH" -X POST $H/hub/installations/my-net/join-codes -d '{"ttl": "24h"}'
# 201 {"code":"ABCD-EFGH-JKMN-PQRS","installation_id":"my-net","expires_at":"…"}

# 3. черновик клуба из CRM (шлюз установки должен быть на связи); ничего не сохраняет
curl -s -H "$AUTH" -X POST $H/hub/installations/my-net/discover -d '{}'
# 200 {"studios":[{"id":"…","name":"Студия Север","enabled":false}, …],"draft":null,
#      "price_lists":[],"notices":[{"code":"STUDIO_REQUIRED",…}]}
curl -s -H "$AUTH" -X POST $H/hub/installations/my-net/discover -d '{"studio": "<id студии>"}'
# 200 {"studios":[…],"studio":"…","draft":{"name":"Студия Север","timezone":"Etc/GMT-3",
#      "slot_minutes":30,"hours":{…},"crm":{"studio":"…"},"courts":[{"id":"court-1","name":"Корт 1",
#      "viva_room":"…","price_list":"…"}, …]},"price_lists":[…],"notices":[…]}

# 4. клуб установки: полный конфиг клуба (черновик после проверки)
curl -s -H "$AUTH" -X PUT $H/hub/installations/my-net/clubs/club-north -d '{
  "name": "Клуб Север", "timezone": "Europe/Moscow", "slot_minutes": 30,
  "hours": {"mon-fri": "07:00-23:00", "sat-sun": "08:00-22:00"},
  "crm": {"studio": "00000000-0000-4000-8000-000000000001"},
  "courts": [{"id": "court-1", "name": "Корт 1", "viva_room": "00000000-0000-4000-8000-000000000011"}],
  "services": {"booking": {"direction": 1, "type": 1}}}'
# 201 (новый) или 200 (заменён) {"installation_id":"my-net","club_id":"club-north","config_version":1}

curl -s -H "$AUTH" $H/hub/installations/my-net            # 200: клубы и состояние шлюза
curl -s -H "$AUTH" -X DELETE $H/hub/installations/my-net/clubs/club-north   # 200 {…,"config_version":2}
curl -s -H "$AUTH" -X DELETE $H/hub/installations/my-net  # 204: установка, её клубы, шлюз и коды
```

| Запрос | Тело | Ответ |
|---|---|---|
| `POST /hub/installations` | `{"installation_id", "name"}` | `201` установка; `409 INSTALLATION_EXISTS` |
| `GET /hub/installations/{id}` | — | `200 {"installation_id", "name", "created_at", "config_version", "clubs": [клуб…], "gateway": строка /hub/status или null}` |
| `DELETE /hub/installations/{id}` | — | `204`; шлюз получает `401` при следующем запросе, неиспользованные коды гаснут |
| `POST /hub/installations/{id}/join-codes` | `{"ttl"?: "24h"}` (до `720h`) | `201 {"code", "installation_id", "expires_at"}` |
| `PUT /hub/installations/{id}/clubs/{club_id}` | конфиг клуба | `201`/`200 {"installation_id", "club_id", "config_version"}`; `400 INVALID_CLUB_CONFIG` с `problems`; `409 CLUB_TAKEN` — клуб у другой установки |
| `DELETE /hub/installations/{id}/clubs/{club_id}` | — | `200 {"installation_id", "club_id", "config_version"}`; партнёры сразу получают `404` |
| `POST /hub/installations/{id}/discover` | `{"studio"?, "days"?, "timezone"?, "slot_minutes"?}` | ответ шлюза: `200 {"studios", "studios_reason"?, "studio"?, "draft", "price_lists", "notices"}`; `503 GATEWAY_OFFLINE`; `502` с кодом CRM |

**Конфиг клуба** — то, что в локальном режиме лежит в `gateway.yaml` в разделах `club`, `venue`,
`courts`, `services`: `name`, `timezone`, `slot_minutes`, `hours`, `crm` (ключи CRM этого клуба —
для Viva `studio`; поверх ключей установки), `courts` (`id`, `name` и ключи драйвера — для Viva
`viva_room`, `price_list`), `services`. Хаб проверяет общую часть (идентификаторы, часовой пояс,
сетку, часы, корты) и отвечает `400` со списком проблем; ключи драйвера проверяет шлюз — если он
конфиг не принял, `GET /hub/installations/{id}` покажет `gateway.config_error`, а
`gateway.applied_config_version` останется прежней.

**Код подключения** одноразовый, хранится только его SHA-256, действует `ttl` (по умолчанию
сутки); повторный, просроченный и неизвестный коды отклоняются одинаково. Новый код для установки,
у которой уже есть шлюз (переустановка, замена компьютера), при использовании заменяет секрет:
прежний шлюз получает `401`. Клуб передаёт код программе `setup` — больше ему ничего не нужно.

**Обнаружение (discover)** выполняется шлюзом установки через его туннель: шлюз читает CRM своей
учётной записью. Для Viva: `GET /studios` даёт все студии учётной записи (новая студия появляется в
списке сама — оператор может её подключить), у выбранной студии — все комнаты как корты (с бронями
и без), часы и часовой пояс из режима работы студии (`workTime`, `offset`), прайс-листы — из
`/pricing`. `enabled` у студии — её уже обслуживает клуб установки (`club_id`). Демо-CRM отдаёт две
студии. Черновик — только черновик: идентификатор клуба выбирает оператор (в пути `PUT`), часовой
пояс из смещения (`Etc/GMT-3`) можно заменить на зону города, всё отмеченное в `notices` — проверить.

### Командная строка (без админ-панели)

```sh
court-gateway hub join-code create -config hub.yaml --installation my-net --name "Моя сеть" [--ttl 24h]
court-gateway hub gateway revoke -config hub.yaml --installation my-net
```

`join-code create` печатает код и адрес хаба (`public_url`); установка, которой хаб ещё не знает,
создаётся при использовании кода. Команду можно выполнять на работающем хабе (в Docker: `docker exec
<контейнер> /court-gateway hub join-code create …`): коды читаются с диска в момент обмена.
`gateway revoke` отзывает секрет шлюза (работающий хаб перестаёт его принимать при следующем
запросе), клубы установки остаются. `--club` — прежнее имя `--installation`.

**Шлюзы прежних версий.** Установка, у которой на хабе нет клубов, обслуживает один клуб с тем же
идентификатором, записанный в её `gateway.yaml`, — так работали шлюзы до установок.

## Ключи партнёров

```yaml
partners:
  - name: aggregator
    key_env: PARTNER_KEY_1          # не короче 24 символов: openssl rand -hex 32
    scopes: [read, book]            # read — сверка; book — ещё и бронирование
    clubs: ["*"]                    # или список клубов
    writes_per_minute: 60           # лимит бронирований по ключу
```

Ключи сравниваются за постоянное время и не попадают в журналы. Клуб, к которому у партнёра нет
доступа, для него выглядит как несуществующий (`404`).

## Мониторинг

**Сигнал идёт от шлюза.** Раз в минуту шлюз делает свою единственную плановую проверку — вход в
CRM и узкий запрос занятости. Её результат пишется в локальный файл состояния (его читает
`healthcheck`) и отправляется хабу по собственному подключению шлюза: `POST /tunnel/heartbeat`
с версией, типом сборки (`release`/`selfbuilt`), `ready` и кодом причины, временем проверки. Хаб
сам шлюз не опрашивает, поэтому CRM клуба видит не больше одной проверки в минуту на шлюз.

Сигнал шлюза — один на установку, сколько бы клубов она ни обслуживала; ниже «клуб» в именах
проверок и метрик — это шлюз установки, а его идентификатор — идентификатор установки (прежние
имена оставлены, чтобы не ломать внешние проверки).

Каждые `heartbeat.interval` (60 с) хаб пересчитывает состояние каждого зарегистрированного клуба:

- `offline` — сигнала нет дольше `offline_after` (3 мин). Открытый туннель без сигналов не
  считается: сигнал перестаёт приходить и тогда, когда шлюз завис, а соединение ещё держится;
- `not_ready` — `ready_failures` (3) сигнала подряд с `ready=false` (`CRM_AUTH_FAILED`,
  `CRM_UNREACHABLE` …); один удачный сигнал сбрасывает счёт;
- `online` — иначе; `pending` — клуб ещё не прислал ни одного сигнала, но и `offline_after` не
  прошло.

Пока сигнала не было, тишина отсчитывается от запуска хаба или от регистрации клуба (что позже):
перезапуск хаба не скрывает мёртвый клуб, а только что подключённый клуб успевает прислать первый
сигнал. Код причины принимается только как короткий код из заглавных букв, версия — только как
номер версии: шлюз не может вписать произвольный текст в то, что видит оператор.

### Файлы для внешней проверки

Если задан `status_dir`, хаб на каждом пересчёте переписывает в нём два файла — каждый атомарно
(временный файл и переименование), так что читатель никогда не видит половину файла. Каталог
должен быть отдельным от `state_dir`: файлы читает другой процесс, а `state_dir` закрыт.

`status.json`:

```json
{"ts": "2030-01-07T12:00:00Z", "ok": false, "version": "0.2.0", "checks": [
  {"check": "club_my_club_online", "ok": true,
   "detail": "«Мой клуб»: last heartbeat 12s ago at 2030-01-07T11:59:48Z (limit 3m0s), version 0.1.0 (release), tunnel connected"},
  {"check": "club_my_club_ready", "ok": false, "detail": "not ready: CRM_AUTH_FAILED, 3 heartbeats in a row (limit 3)"}
]}
```

`metrics` — строки `ключ=число`:

```
check_club_my_club_online=1
check_club_my_club_ready=0
club_my_club_last_seen_age_seconds=12
club_my_club_outdated=1
clubs_total=1
clubs_online=1
clubs_ready=0
status_ok=0
run_last_utc_epoch=1894017600
```

На каждый клуб две проверки: `club_<id>_online` и `club_<id>_ready`; `ok` верхнего уровня —
`false`, если не прошла хоть одна. Пока клуб `offline`, `club_<id>_ready` остаётся `ok: true` с
пояснением «unknown while offline»: одна причина — одна тревога. В идентификаторе клуба дефис
заменяется на `_`. Ключ метрики — `[a-z][a-z0-9_]*`, значение — обычное десятичное число не
длиннее 15 цифр, ключи не повторяются (неподходящий ключ в файл не попадает и пишется в журнал).
`club_<id>_last_seen_age_seconds` есть только у клубов, от которых был сигнал; `club_<id>_outdated`
— 1, если версия шлюза ниже `latest_version`. Секретов в файлах нет: только id и название клуба,
время, версия, тип сборки и коды причин.

Как и куда доставлять тревоги, решает внешняя проверка, которая читает эти файлы; по `ts` и
`run_last_utc_epoch` она замечает и остановившийся хаб.

### Webhook (необязательно)

Оператор без своей системы проверок может включить `alerts.webhook_url_env`: хаб отправит POST
JSON `{event, club, club_name, text, time}` при смене состояния клуба (`event` — `offline`,
`online`, `not_ready`, `ready`). По умолчанию выключено. Ошибки доставки пишутся в журнал без
адреса: в адресе webhook обычно есть токен.

## Состояние шлюзов

```sh
curl -s -H "Authorization: Bearer $HUB_OPERATOR_KEY" https://hub.example.test/hub/status
```

Одна строка — один шлюз (установка); поле `club` в ней — идентификатор установки (прежнее имя
поля, оставлено для совместимости). `applied_config_version`, `config_error` и `clubs_served` —
что шлюз сообщил о конфигурации клубов, на которой работает.

```json
{"time": "…", "latest_version": "0.2.0", "clubs": [
  {"club": "my-club", "name": "Мой клуб", "connected": true, "last_seen": "…",
   "state": "online", "last_heartbeat": "…",
   "version": "0.1.0", "build": "release", "platform": "windows-amd64", "outdated": true,
   "ready": true, "last_check": "…", "registered_at": "…",
   "applied_config_version": 3, "clubs_served": ["club-north", "club-south"]}
]}
```

`connected`/`last_seen` — состояние туннеля, `state`/`last_heartbeat` — по сигналам шлюза,
`last_check` — время проверки по часам шлюза. `build: selfbuilt` — клуб собрал программу сам, она не обновляется автоматически; `outdated` —
версия ниже `latest_version`. Если задать `latest_version`, хаб подсказывает официальным сборкам
обновиться сразу, не дожидаясь суточной проверки.

## Выпуски и подписи

Автообновление доверяет только манифесту, подписанному ключом выпусков (ed25519). Открытый ключ
вшивается в официальные сборки (`-X main.releaseKey=…`) и публикуется в репозитории как
`release.pub`; закрытый ключ хранится вне репозитория и никогда не коммитится.

```sh
go run ./tools/release keygen -out release.key        # один раз; печатает открытый ключ → release.pub
RELEASE_KEY="$(cat release.pub)" VERSION=0.2.0 scripts/build.sh
```
